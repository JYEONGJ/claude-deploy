# ROADMAP_01: 인형 판매 사이트 (테스트용 최소 기능) 요구사항 분석

## 1. 개요

- **서비스 목적**: 로그인 없이 인형 상품을 조회하고 구매할 수 있는 간단한 판매 사이트.
- **범위**: 테스트용 MVP. 비기능 요구사항(성능, 보안 강화, 결제 연동, 주문 이력 등)은 제외한다.
- **핵심 데이터**: 인형(Doll). 상품명, 가격, 재고를 가진다.
- **사용자 구분**: 사용자와 관리자를 구분하지 않는다. 로그인이 없으므로 등록/수정/삭제 기능도 누구나 호출할 수 있다. 테스트 목적이므로 허용하되, 실서비스 전환 시 반드시 인증을 추가해야 한다.

## 2. 기능 요구사항

### 2.1 필수 기능 (MVP)

| ID | 기능 | 설명 | 우선순위 |
|----|------|------|----------|
| F-01 | 인형 목록 조회 | 등록된 모든 인형을 상품명, 가격, 재고와 함께 목록으로 보여준다. | 필수 |
| F-02 | 인형 상세 조회 | 인형 한 개의 상품명, 가격, 재고를 보여준다. 구매 버튼을 포함한다. | 필수 |
| F-03 | 인형 등록 | 상품명, 가격, 재고를 입력하여 새 인형을 등록한다. | 필수 |
| F-04 | 인형 수정 | 기존 인형의 상품명, 가격, 재고를 변경한다. | 필수 |
| F-05 | 인형 삭제 | 인형을 삭제한다. | 필수 |
| F-06 | 구매 및 재고 차감 | 구매 수량만큼 재고를 줄인다. 재고가 부족하면 구매를 거절한다. | 필수 |

### 2.2 입력 검증 규칙

| 항목 | 규칙 |
|------|------|
| name (상품명) | 필수. 공백 제외 1자 이상, 100자 이하. |
| price (가격) | 필수. 정수, 0 이상. 단위는 원(KRW)으로 가정한다. |
| stock (재고) | 필수. 정수, 0 이상. |
| quantity (구매 수량) | 필수. 정수, 1 이상. |

### 2.3 비즈니스 규칙

- BR-01: 재고가 구매 수량보다 적으면 구매를 실패시키고 재고는 변하지 않는다 (HTTP 409).
- BR-02: 재고 차감은 원자적으로 처리한다. 예를 들어 `UPDATE ... SET stock = stock - :qty WHERE id = :id AND stock >= :qty` 형태로, 동시 구매에도 재고가 음수가 되지 않도록 한다.
- BR-03: 재고가 0인 인형도 목록과 상세에는 보이되, 구매 버튼은 비활성화하고 "품절" 표시를 한다.
- BR-04: 삭제는 물리 삭제로 처리한다 (테스트용). 주문 테이블이 없으므로 참조 무결성 문제는 없다.

### 2.4 제외 범위 (Out of Scope)

- 로그인, 회원가입, 권한 관리
- 장바구니, 주문 이력, 결제 연동, 배송
- 이미지 업로드, 카테고리, 검색, 정렬, 페이지네이션 (목록이 적다는 가정)
- 관리자 대시보드, 통계

## 3. 데이터 모델

### 3.1 Doll 엔티티

| 필드 | 타입 | 제약 | 설명 |
|------|------|------|------|
| id | Int | PK, autoincrement | 인형 고유 ID |
| name | String | 필수, 최대 100자 | 상품명 |
| price | Int | 필수, 0 이상 | 가격 (원) |
| stock | Int | 필수, 0 이상, 기본값 0 | 재고 수량 |
| createdAt | DateTime | 기본값 now() | 등록 시각 |
| updatedAt | DateTime | 자동 갱신 | 수정 시각 |

### 3.2 Prisma 스키마 초안 (참고용)

```prisma
model Doll {
  id        Int      @id @default(autoincrement())
  name      String   @db.VarChar(100)
  price     Int
  stock     Int      @default(0)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

- 샘플 데이터: 인형 3~5건 (재고 0인 건 1건 포함, 품절 화면 확인용).
- 주문 테이블은 MVP에서 만들지 않는다. 구매는 재고 차감만 수행하고 이력은 남기지 않는다. 이력이 필요해지면 `Order` 모델을 추가한다.

## 4. API 목록 (초안)

공통: Base URL `/api`, 요청/응답 형식 JSON, 인증 없음.
오류 응답 형식: `{ "error": { "code": "...", "message": "..." } }`

| # | Method | Path | 기능 | 요청 Body | 성공 응답 | 주요 오류 |
|---|--------|------|------|-----------|-----------|-----------|
| A-01 | GET | `/api/dolls` | 인형 목록 조회 (F-01) | - | 200, `Doll[]` | - |
| A-02 | GET | `/api/dolls/:id` | 인형 상세 조회 (F-02) | - | 200, `Doll` | 404 존재하지 않음 |
| A-03 | POST | `/api/dolls` | 인형 등록 (F-03) | `{ name, price, stock }` | 201, `Doll` | 400 검증 실패 |
| A-04 | PUT | `/api/dolls/:id` | 인형 수정 (F-04) | `{ name, price, stock }` (전체 필드) | 200, `Doll` | 400, 404 |
| A-05 | DELETE | `/api/dolls/:id` | 인형 삭제 (F-05) | - | 204 | 404 |
| A-06 | POST | `/api/dolls/:id/purchase` | 구매 및 재고 차감 (F-06) | `{ quantity }` | 200, `{ id, name, price, stock }` (차감 후 재고) | 400 수량 오류, 404, 409 재고 부족 |

### 4.1 API 세부 메모

- A-04는 테스트 단순화를 위해 PUT으로 전체 필드를 받는다. 부분 수정(PATCH)은 범위에서 제외한다.
- A-06은 구매 주문 리소스를 만들지 않고, 인형 재고를 차감하는 동작으로만 정의한다.
- 가격 및 재고는 음수를 허용하지 않는다 (검증 실패 시 400).

## 5. 화면 목록 (초안)

| # | 화면명 | 경로 | 주요 구성 | 연결 API |
|---|--------|------|-----------|----------|
| S-01 | 인형 목록 | `/dolls` | 인형 카드 또는 표 (상품명, 가격, 재고, 품절 표시), 상세 이동 링크, "인형 등록" 버튼 | A-01 |
| S-02 | 인형 상세 | `/dolls/:id` | 상품명, 가격, 재고, 수량 입력, "구매하기" 버튼, "수정" 및 "삭제" 버튼 | A-02, A-06, A-05 |
| S-03 | 인형 등록 | `/dolls/new` | 상품명, 가격, 재고 입력 폼, 저장 및 취소 | A-03 |
| S-04 | 인형 수정 | `/dolls/:id/edit` | 기존 값이 채워진 입력 폼, 저장 및 취소 | A-02, A-04 |

### 5.1 화면 공통 메모

- 구매 완료 후 S-02에서 차감된 재고를 즉시 반영한다.
- 구매 시 재고 부족(409)이면 "재고가 부족합니다" 메시지를 표시한다.
- 삭제 전 확인 창(confirm)을 띄운다.
- 입력 오류는 필드 옆에 메시지로 표시한다.

### 5.2 SEO 관련 메모 (프로젝트 seo-rule 준수)

- S-01, S-02는 상품 페이지이므로 서버 사이드 렌더링(SSR)으로 상품명과 가격이 포함된 HTML을 응답한다.
- S-02는 `<title>`, `<meta name="description">`, OpenGraph, JSON-LD(Product)를 서버에서 채워서 내려준다.
- 등록, 수정 화면(S-03, S-04)은 `<meta name="robots" content="noindex, nofollow">`를 명시한다.
- 제목 형식: `인형 목록 | 사이트명`, `{상품명} | 사이트명`.

## 6. 구현 로드맵 (단계별)

| 단계 | 작업 | 산출물 | 완료 기준 |
|------|------|--------|-----------|
| 1 | Prisma 스키마 작성 및 마이그레이션, 샘플 데이터 시드 | `prisma/schema.prisma`, 시드 스크립트 | DB에 Doll 테이블 생성, 샘플 데이터 조회 가능 |
| 2 | 목록 및 상세 조회 API (A-01, A-02) | 라우터, 서비스 | curl 또는 브라우저에서 JSON 응답 확인 |
| 3 | 등록, 수정, 삭제 API (A-03 ~ A-05) with 검증 | 검증 모듈, 라우터 | 잘못된 입력에 400 반환 확인 |
| 4 | 구매 API와 원자적 재고 차감 (A-06) | 구매 서비스 | 재고 부족 시 409, 동시 요청에도 재고가 음수가 되지 않음 |
| 5 | 화면 S-01 ~ S-04 구현 (SSR) | 템플릿, 정적 자산 | 각 화면이 API와 연결되어 동작 |
| 6 | SEO 메타데이터, JSON-LD, sitemap.xml, robots 설정 | 메타 태그, sitemap | 상품 페이지마다 고유 title, description 존재 |
| 7 | 통합 테스트 (주요 시나리오) | 테스트 코드 | 등록 후 조회, 구매 후 재고 감소, 삭제 후 404 시나리오 통과 |

## 7. 권장 디렉토리 구조 (참고)

현재 `claude_pipeline` 디렉터리에는 `.claude`, `.env`, `.vscode`, `node_modules`, `package.json`, `prisma`, `yarn.lock`이 있다. 이를 기준으로 다음 구조를 권장한다.

```
claude_pipeline/
├── prisma/
│   ├── schema.prisma          # Doll 모델
│   └── seed.js                # 샘플 인형 데이터
├── src/
│   ├── server.js              # 진입점 (HTTP 서버, 라우팅 등록)
│   ├── db.js                  # Prisma Client 싱글톤
│   ├── routes/
│   │   └── dolls.js           # /api/dolls 라우터 (A-01 ~ A-06)
│   ├── services/
│   │   └── dollService.js     # 조회, 등록, 수정, 삭제, 구매(재고 차감) 로직
│   ├── validators/
│   │   └── dollValidator.js   # 입력 검증 규칙 (2.2절)
│   ├── views/                 # SSR 템플릿 (S-01 ~ S-04)
│   │   ├── dolls-list.html
│   │   ├── doll-detail.html
│   │   ├── doll-form.html     # 등록/수정 공용
│   │   └── layout.html        # 공통 head (메타, OpenGraph, 공통 헤더)
│   └── public/                # 정적 자산 (CSS, JS)
├── tests/
│   └── dolls.test.js          # 통합 테스트 (7단계)
├── sitemap.xml                # 상품/목록 URL
├── robots.txt                 # 관리 화면 차단 설정
├── package.json
└── .env
```

- `esbuild`는 서버 번들링 또는 클라이언트 JS 번들링에 사용할 수 있다.
- 테스트 목적이므로 구조는 단순하게 유지하고, 필요 이상의 계층(레포지토리 계층 등)은 만들지 않는다.

## 9. 확인이 필요한 가정 (Open Questions)

- 가격 단위를 원(KRW) 정수로 가정했다. 소수점 가격이 필요한지 확인이 필요하다.
- 구매 시 구매자 정보(이름, 연락처)를 받지 않는다고 가정했다.
- 목록 페이지네이션은 제외했다. 인형 수가 많아질 경우 추가가 필요하다.
- 인증 없이 등록, 수정, 삭제를 허용한다. 테스트 전용이며, 공개 배포 시에는 반드시 관리자 인증을 추가해야 한다.
